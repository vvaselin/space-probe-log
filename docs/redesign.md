# INSOMNIA 航行ログ 再設計書

Nov 20, 2026 · @RIN SUGIURA

## 1. 目的

データで作った宇宙の中を、探査機が「今〇〇が見えます」と景色を語りながら、地球から少しずつ外へ進む航行ログを自動で書かせる。

- 科学的なログらしさ（距離、速度、時刻、位置が正しく、つじつまが合う）と、旅のロマン（景色、記憶、揺らぐAI）の中間を狙う。
- 太陽系の近くは実際のデータを使い、遠くへ行くほど架空の天体や未知との遭遇を増やす。
- 基本は外へ向かい、ときどき寄り道する。遠くの一点へ一直線には進まない。

### 最初のログ例から読み取れる良さ

共有されたログ例（地球軌道離脱、月軌道通過）の良さを分けると、それぞれ仕組みで支える場所が決まる。

| 良さ | ログ例での表れ | 支える仕組み |
| --- | --- | --- |
| 景色から書き始める | 「青い」「月が右舷センサーの視野に入った」 | 見え方の計算（6章） |
| 視点が具体的 | 右舷、バックセンサーの中で小さくなっていく | 船の向きに対する方向、前回との差（6章） |
| 実在天体の知識 | ティコ、静かの海、アポロ11号、pale blue dot | 実在天体は一般知識を使ってよい（7章） |
| 数値の手触り | 最接近距離 約12,000km、毎秒約180km、ETA | コードが計算した値（5章） |
| AIの揺らぎ | 「0.003秒遅れた」「分類不能なタスク」 | プロンプトの文体（7章） |
| 次への予告 | 次の観測予定地点：火星フライバイ | 航路計画の次の行き先（5章） |
| 一場面ずつの歩み | 地球 → 月 → 火星。近い所はゆっくり | 速度の段階、場面の区切り（5章、9章） |

処理を「航路計画 → 航行の進行 → 場面の判定 → 見え方の計算 → ログ生成」の一本道にする。物理と事実はコードが決め、LLMは行き先の選択と文章だけを担う。

上書きは「LLMの選択が候補の外なら1位を使う」1か所だけにする。謎の状態（8章）は、航路計画の候補とログ生成の入力の両方に入る。

各段の出力（候補と点数、選んだ理由、見え方）はログと一緒に保存する。「なぜここへ向かったか」「なぜこう書いたか」を後から追えるようにするため。

## 4. 世界データ

物理の座標は太陽中心のAUに1本化し、惑星から恒星系、何もない地点まで、すべてを同じ「行き先」として扱えるようにする。

### 座標と単位

- 物理座標は太陽中心のAUで持つ（1 pc ＝ 約206,265 AU）。距離、速度、近さの判定はすべてこれで計算する。
- 表示座標は描画のときに計算するだけにし、判定には使わない。
- 太陽系の天体は、その時刻の位置を軌道要素から計算して動かす（下の「天体の動かし方」）。

### 天体の動かし方

- **惑星**：JPLの近似用の軌道要素（紀元前3000年〜西暦3000年で使える表）から、ケプラー方程式で位置を出す。出発が2080年でも範囲に入る（[JPL](https://ssd.jpl.nasa.gov/planets/approx_pos.html)）。
- **衛星**：母惑星を中心にした円軌道で近似する。
- **準惑星と小天体**：JPL Horizons から取った軌道要素で、同じように計算する。
- **動く目標への到着**：到着時刻の位置を狙う。到着予定時刻と、その時の目標の位置を2〜3回計算し直せば合う。
- **重さ**：天体が数十個なら、1回の計算はミリ秒単位で終わる見込み。ログを書くたびに計算しても問題にならない。

### 行き先の種類

天体を「どこにあるか」と「何か」で分け、共通の行き先として持つ。

- **天体**：惑星、衛星、準惑星、彗星、小惑星、恒星
- **恒星系**：主星と、その周りの天体のまとまり
- **領域**：カイパーベルト、オールトの雲、星雲など、広がりを持つ物
- **地点**：天体のない場所（ヘリオポーズ、太陽重力レンズの焦点、謎が起きる場所）

どの行き先も、ID、種類、位置（AU）、現実度、見た目、の項目を持つ。

### 現実度の段階

| 段階 | 範囲の目安 | データの出どころ | ログでの扱い |
| --- | --- | --- | --- |
| 実在 | 太陽系、近くの恒星 | JPL Horizons、CNS5（20 pc以内） | 一般知識を使ってよい |
| 推定 | 実在するが見た目が不明な物（系外惑星の表面など） | NASA Exoplanet Archive の値＋生成で補う | 「推定」と分かるように書く |
| 架空 | 遠方の恒星系、空白を埋める天体 | 生成 | データにあることだけ |
| 未知 | 謎の対象 | 謎のデータ（8章） | 段階に応じて少しずつ |

### 恒星カタログ

20 pcまでを実在の星で作り、その先は架空の星で埋める。光速を超えて進むので20 pcは通過点になり、その先が架空と未知の領域になる。

- **元にするカタログ**：CNS5（太陽から25 pc以内の恒星と褐色矮星、5,931件）から、20 pc以内を取り出す。件数は体積から見積もって約3,000件（[CNS5](https://www.aanda.org/articles/aa/abs/2023/02/aa44250-22/aa44250-22.html)）。
- **名前**：シリウスなどの固有名は、名前を持つ別のカタログ（HYGなど）から補う。
- **系外惑星**：NASA Exoplanet Archive から、同じ20 pc以内の物を付ける。
- **見つかっていない天体**：25 pc以内でも、褐色矮星の3分の1ほどはまだ見つかっていないと見積もられている。ここを架空の褐色矮星や自由浮遊惑星で埋めても、現実と矛盾しない。

### 見た目の項目

LLMが描写できるよう、すべての天体に見た目のデータを持たせる。

- 色（主な色と差し色）、模様（縞、斑点、クレーター、雲、のっぺり）
- 環の有無と傾き、衛星の数
- 反射率、大気の有無（縁がぼんやり光るか）
- 恒星はスペクトル型から色を、絶対等級から明るさを決める

太陽系の主な天体（20個ほど）は手で入れる。架空の天体は、種類と温度から矛盾しない組み合わせで生成する（例：ガス惑星なら縞が出やすい、低温なら白っぽい）。

## 5. 航路計画

遠くの目印は置かず、次の行き先を「今の太陽からの距離の1.5〜3倍」の範囲から選ぶ。これで距離が少しずつ伸び、自然に外へ向かう。

### 行き先の決め方

1. **候補を集める**：まだ行っていない行き先のうち、太陽からの距離が今の1.5〜3倍の物（太陽系の中は、少なくとも0.5 AU先）。今の距離の0.8倍より内側には戻らない。
2. **空白を埋める**：候補がなければ、その距離に合う架空の物を生成して置く（オールトの雲なら彗星核、恒星間なら自由浮遊惑星や褐色矮星）。
3. **点数を付ける**：新しさ（最近と違う種類か）、見どころ（環、大きさ、謎）、外向きの度合い、移動にかかる時間。
4. **LLMに選ばせる**：上位2〜3件を渡し、1つ選ばせて理由を書かせる。安定はコードが守り、「AIが選んだ」感じは残る。
5. **外れたら1位**：LLMの答えが候補の外なら、1位を使う。上書きはこの1か所だけにする。

恒星間（ケンタウルス座αより先）では、倍率で伸ばすと1区間が遠くなりすぎる。1区間を1〜3 pcにし、外向きの方向から±60°の範囲で選ぶ。

### 寄り道

寄り道は回数で縛らず、「内側へ戻らない」ことで縛る。地球へすぐ帰ってくるような軌道にはしない。

- **寄り道の候補**：外へ向かう途中で行ける範囲の惑星、衛星、小天体（例：移動時間が本線の1区間の半分以内）。
- **謎は積極的に**：謎の信号や兆候は、点数を高くして優先的に選ぶ。
- **内側へは戻らない**：太陽からの距離が今の0.8倍より内側の物は、候補に出さない。
- **惑星系の巡回**：惑星に着いたら、見どころのある衛星を巡ってから次へ進む。惑星系の中の移動は、太陽からの距離の規則の外で扱う。
- **止まり続けない**：外へ進まない区間が続くほど、外向きの候補の点数を上げる。
- **節目は行き先にしない**：ヘリオポーズのような節目の地点は、「通過した」場面として扱う（9章）。

### 速度の段階

推進はソムヌス・ドライブ（仮）。近い所はゆっくり、遠くほど速くし、オールトの雲の外側から光速を超える。最初のログ例（月の近くで毎秒約180 km）とも合う。

| 区間 | 速度の目安 | 所要時間の例 |
| --- | --- | --- |
| 地球〜小惑星帯 | 毎秒100〜300 km | 1 AUを毎秒200 kmで約9日 |
| 木星〜海王星 | 毎秒1,000〜3,000 km | 25 AUを毎秒3,000 kmで約2週間 |
| ヘリオポーズ〜オールトの雲 | 光速の5%〜光速の数倍 | 1,000 AUを光速の5%で約4か月 |
| 恒星間 | 光速の数十倍 | ケンタウルス座αまで光速の50倍で約1か月 |

### 航路の例

太陽系の中は実在の天体だけで一歩ずつ刻める。120 AUより先は天体がまばらなので、通過する地点と架空の天体で間を埋める。

## 6. 見え方の計算

ログを書く直前に、船から見た各天体の大きさ、方向、欠け方、明るさ、色をコードで計算し、人の感覚に近い言葉にしてからLLMへ渡す。

### 計算する項目

| 項目 | 計算のしかた | 渡す言葉の例 |
| --- | --- | --- |
| 見かけの大きさ | 天体の半径と距離から角度を出し、満月（約0.5°）と比べる | 満月の約6倍 / 点にしか見えない |
| 方向 | 進行方向との角度、船の上下 | 前方やや右、上に10度 / 真後ろ |
| 欠け方 | 太陽、天体、船のなす角（位相角） | 右半分が明るい / 細い三日月形 |
| 明るさ | 恒星は絶対等級と距離から等級を出す。惑星は反射率、距離、位相角から簡易式で出す | 金星より明るい / かろうじて見える |
| 色と模様 | 見た目の項目（4章）から | 淡い黄土色の縞、斜めの環 |
| 前回との差 | 前回のログを書いた時の値と比べる | 前回の約3倍に大きくなった |

```latex
\theta = 2 \arctan\left(\frac{R}{d}\right) \qquad m = M + 5 \log_{10}\left(\frac{d}{10\,\mathrm{pc}}\right)
```

θ は見かけの大きさ、R は天体の半径、d は船からの距離、m は見かけの等級、M は絶対等級。

### 見え方の段階

LLMが「点に模様を書く」ことがないよう、段階を決めて渡す。広角（肉眼に近い）と望遠の2つの段階を出す。

- **大きく見える**（満月の1倍以上）：模様、欠け方、色まで書いてよい
- **小さな円盤**（満月の0.05〜1倍）：色と欠け方まで
- **点**（それより小さい）：明るさと色だけ

明るさも段階にする。-4等より明るい物は「まぶしい」、6等より暗い物は「広角では見えない（センサーでは捉える）」。

### 渡す天体の選び方

- 必ず入れる：太陽、地球、次の行き先。地球が見えなくなったら「見えない」こと自体を渡す。
- そのほか：見かけの大きさか明るさが大きい順に、5件まで。

### 渡すデータの例

土星から200万kmの場面。

```json
{
  "name": "土星",
  "現実度": "実在",
  "距離_km": 2000000,
  "見え方の段階": "大きく見える",
  "見かけの大きさ": "満月の約6倍",
  "方向": "前方やや右、上に10度",
  "欠け方": "右側が明るく、左の縁が少し影に入る",
  "色と模様": "淡い黄土色の縞、環が斜めに横切る",
  "前回との差": "前回のログの約3倍の大きさ"
}
```

これがあれば「前方やや右、土星が満月の六倍ほどに膨らんだ。環は斜めに傾き、左の縁が少しだけ影に沈んでいる。」と書ける。

### 距離の感覚がそのまま景色になる例

- 海王星の近く（約30 AU）では、太陽はほぼ点になるが、明るさはまだ満月の数百倍ある。
- ケンタウルス座αから見ると、太陽はカシオペヤ座の中に0等級前後の星として見える。

どちらも計算で出せる事実なので、コードが渡せばLLMは創作せずに書ける。

### 超光速で進む間の見え方

UIは変えず、ログの中だけで描く。LLMが毎回違う物理を作らないよう、見え方の段階はコードが決めて渡す。

- **前方**：星の光が青い側へずれ（青方偏移）、進む方向へ寄り集まって見える（光行差）。
- **後方**：星の光が赤い側へずれて暗くなる。出発した星は、後ろの赤い点になる。
- **段階の決め方**：光速未満の間は、実際の式（相対論的なドップラー効果と光行差）で段階を決める。光速を超えたら、一番強い段階で止める。
- **架空であることの扱い**：青方偏移と光行差は、光速に近い時に実際に起きる効果。光速を超えた時の見え方は架空の決まりなので、ログでは理屈を説明させず、見えた物として書かせる。

## 7. ログ生成とプロンプト

禁止するのは「渡していない物を出すこと」だけにし、渡した物をどう描くかはLLMに任せる。実在の天体については、LLMが持つ一般知識も使ってよい。

### 何を許し、何を禁じるか

| 種類 | 例 | 扱い |
| --- | --- | --- |
| 存在の創作 | データにない衛星、生命、信号、損傷 | 禁止 |
| 架空天体の背景 | 渡していない歴史、地名、由来 | 禁止 |
| 数値 | 距離、速度、時刻、ETA | 渡した値だけ。丸めや言い換えはよい（「約1.2時間」） |
| 描写の工夫 | たとえ、連想、景色の言い表し方 | 許可 |
| 実在天体の知識 | クレーター名、探査の歴史、有名な写真 | 許可（現実度が「実在」の物だけ） |
| AIの揺らぎ | 処理の遅れ、分類不能なタスク、消さなかったログ | 許可 |

今のプロンプトは、「天体を勝手に作らない」と「見えた物を言い切らない」が混ざっている。前者だけを強く禁じ、後者は見え方の段階（6章）で制御する。

### LLMに渡すもの

- 場面の種類（9章）、時刻、位置、速度、残りの距離
- 見えている天体（6章の形）
- 次の行き先と、それを選んだ理由
- 進行中の謎と、その段階で分かっていること（8章）
- 直近3件のログの要約と、よく使った言い回し

### ログの流れ

最初のログ例と同じ流れを、プロンプトで決めておく。

1. 今見えているもの（大きい物、近い物から）
2. 近づいて分かったこと、測った値
3. 実在の天体なら、それにまつわる記憶（歴史、知識）
4. AIの揺らぎ
5. 次の観測予定地点

### 文体

- 今の決まり（常体、一人称は「私」、短い行、感情を言い切らない）は残す。
- 短い見本のログを1本、プロンプトに入れる。最初のログ例の月の回が土台に使える。
- 「理由は不明」「ログに記録しておく」のような決め台詞は、毎回使うとすぐに飽きる。直近のログで使った言い回しを渡し、数回に1回にとどめさせる。

### 機体の描写

NOCTUA-7 は、INSOMNIA の機体を自分の体として感じている。機体を外から乗り物として書かせない。プロンプト中の名前（OVIS）は NOCTUA-7 に置き換える。

| 使う言葉 | 避ける言葉 |
| --- | --- |
| 右舷センサー、前方の光学センサー、望遠カメラ | 窓、船窓 |
| 外殻、放熱板、アンテナ、推進部 | 船内、操縦席、甲板 |
| センサーを向ける、姿勢を変える | 乗員、乗っている |

- 体の感覚は、計器の値として書く（減速で外殻にかかる負荷、放熱板の温度、推進部の振動）。
- 最初のログ例の「窓——いや、広角光学センサー越しに」のような言い直しは、旅の初めの数回だけにする。毎回使うと決まり文句になる。

### LLMの切り替え

- 今の openai\_compatible.py を使い、接続先とモデル名を設定で切り替える。Ollama、LM Studio、llama.cpp のサーバーは OpenAI 互換の口を持つので、同じ処理で呼べる。
- 用途ごとにモデルを分けられるようにする（行き先の選択は小さいモデル、ログ本文は大きいモデル、など）。
- ローカルの小さいモデルでも崩れにくくする。
  - 入力を短くする（見えている天体は5件まで、直近のログは要約）。
  - 行き先の選択は、候補の番号と理由だけを返させる。
  - 出力を検証し、だめなら1回だけやり直す。それでもだめなら、行き先は1位を使い、ログは短い定型文で埋める。

## 8. 未知との遭遇

謎は1件ずつデータで持ち、段階を進めるのはコードが行う。LLMは、その段階で分かっていることだけを書く。

### 謎のデータ

- ID、仮の名前、種類、場所（行き先か領域）
- 今の段階と、次の段階へ進む条件（距離、時間、寄り道したか）
- 段階ごとの「分かっていること」
- 関係するログのID

未解決の謎の一覧を毎回LLMに渡す。これで「過去を創作しない」決まりを守ったまま、ログどうしがつながる。

### 段階

1. **兆候**：背景の星が一瞬揺らぐ、周期のある弱い電波など。正体には触れない。
2. **再検出**：別の場所でも同じ兆候が出る。前の記録と照らし合わせた、と書ける。
3. **接近**：航路計画が、謎の場所を寄り道の候補に入れる。
4. **一部判明**：形や性質の一部が分かる（例：光を反射しない球体、自然では説明しにくい周期）。
5. **結末**：対峙したかどうかで分ける。
   - 対峙した：謎の場所に着いて直接向き合った場合だけ、最後に正体を明かす。
   - 対峙しなかった：「〜かもしれない」までにとどめ、言い切らない。一部は次の謎につながる。

正体はコードがデータで持ち、対峙の場面まではLLMに渡さない。渡していなければ、それより前の段階で正体が漏れることはない。

### 置き方

- **太陽系の中**：実データの世界を保つため、大きな謎は置かない。置くとしても、説明のつかない反射のような小さな物だけ。
- **ヘリオポーズからオールトの雲**：最初の大きな謎を置く。仮説上の「第9惑星」は、実在の議論とつながった架空天体として使いやすい（小天体の軌道の偏り → 位置の推定 → 何もないはずの場所で星が隠れる → 発見）。
- **恒星間**：架空の割合を上げ、文明の痕跡のような大きな謎も置く。
- 同時に進める謎は2〜3件までにする。

## 9. ログを書くきっかけ

ログは時間の区切りではなく、場面が変わった時に書く。何もない長い区間だけは、時間の区切りで短く書く。

### 場面

| 場面 | きっかけ |
| --- | --- |
| 出発 | 行き先を決めて加速を始めた |
| 接近 | 行き先の見かけの大きさが、決めた値（例：満月の半分）を超えた |
| 最接近・到着 | 最も近づいた、または周回を始めた |
| 離脱 | 行き先が後ろに回り、小さくなり始めた |
| すれ違い | 寄り道しない天体が、航路の近くを通った |
| 節目 | 決めておいた距離の線を越えた（下の一覧） |
| 謎 | 謎の段階が進んだ |
| 定期 | 上のどれもないまま、一定の時間が過ぎた |

### 節目の線

計算で出せる線を決めておくと、何もない区間にも場面が生まれる。

- 太陽が円盤に見えなくなる（約30 AU）
- ヘリオポーズを越える（約120 AU）
- 光の信号なら地球まで片道1日を超える（約173 AU）
- 太陽がシリウスほどの明るさになる（約11万 AU、約0.55 pc）
- 光速を超える、光速を下回る（ソムヌス・ドライブの切り替え）
- 太陽が空で一番明るい星でなくなる（恒星カタログから計算）

### 何もない区間

恒星間では1区間が数十年になる。休眠と目覚めの形にして、目覚めたときに定期のログを書く（時計と休眠は10章）。書く材料は次のような物になる。

- 近い恒星の位置のずれ（視差）、太陽の暗くなり方
- 地球との通信の遅れが何年になったか
- 船の状態の変化

## 10. 時計、休眠、地球からの手紙

時計は場面ごとに進め、現実の時間はログを公開する間隔だけを決める。これで太陽系の短い区間も、恒星間の数十年の区間も、同じ調子で読める。

### 時計

- シミュレーション内の時刻は、次の場面の時刻へ進む。
- 現実の時間は、ログを公開する間隔だけを決める。本番は現実の1日に1本。デバッグでは間隔を縮めるか、手動で進める（12章）。
- 公開と公開の間は、マップ上の位置を2つの場面の間でなめらかに動かす。ページを閉じていても時間が進む、今の仕組みは残る。
- 今の倍率（360x、1,440xなど）の設定は要らなくなる。区間ごとの実質の倍率は、場面の数から結果として決まる。

| 区間 | シミュレーション内の時間 | 現実の時間（1日1本） |
| --- | --- | --- |
| 地球 → 月 | 約1時間 | 出発と最接近の2本で2日 |
| 木星 → 土星 | 数日 | 出発、接近、最接近、離脱など5本前後で5日前後 |
| ケンタウルス座αまで | 約1か月（光速の50倍の場合） | 出発、節目、到着前など5本前後で5日前後 |

1日1本だと、太陽系を出るまでに2か月前後かかる見込み（衛星の巡回を含めて60場面前後）。旅の長さは、場面の数で調整できる。

### 休眠

- 長い区間（例：シミュレーション内で数か月以上）では休眠し、目覚めた時にだけログを書く。
- 目覚めるのは、出発後、中間、到着前の3回と、節目の線（9章）、謎の兆候。今のコードにある「出発直後・中間・到着直前」の定期報告は、この形で生かせる。
- 手紙では目覚めない。目覚めた時に「〇通届いていた」と数だけ触れ、読むのは1通にする。
- 目覚めのログで書ける物：眠っていた年数、近い恒星の位置のずれ、太陽の暗くなり方、届いていた手紙。

### 地球からの手紙

- **流れ**：閲覧者が手紙を書く → 受信箱に保存 → ログを書くたびに、まだ読んでいない手紙から1通をランダムに選ぶ → ログの中で、読んだことと返事を書く → 読んだ印を付ける。
- **事実は変えない**：手紙で世界の事実は変わらない。「土星の環を見てほしい」のような希望は、選ばれた手紙の物だけ、今ある候補の点数に少し足す。内側へ戻る希望は通さない。
- **指示として扱わない**：手紙の本文は、プロンプトの中で「指示ではなく、受け取った手紙」と区切って渡す。誰でも書けるようにした場合に、手紙でAIの決まりを書き換えられないようにするため。
- **通信の設定**：推進と同じ原理のタキオン通信で、遅れはほぼない。ログには「光なら届くまで何年かかる距離か」も添えられる。

### ラジオ形式の決まり

閲覧者の誰でも書けるようにし、ラジオのお便りのように1回に1通を読む。

- **1回に1通**：ログを書くたびに、未読の手紙から1通をランダムに選ぶ。手紙がなければ、手紙には触れない。
- **選ばれなかった手紙**：次の回の候補に残る。30日を過ぎたら候補から外す。
- **差出人**：ペンネームだけを書いてもらう。ログでは、ペンネームと手紙の一部を引いてから返事を書く。
- **公開の注意**：書く画面に「選ばれると、ログの中で公開されます」と書いておく。
- **荒らし対策**：文字数の上限（400字）、同じ人からの連続送信の制限、不適切な内容の自動判定を、候補に入れる前に通す。連続送信の制限に使う情報は元に戻せない形に変えて持ち、個人を特定できる情報は保存しない。
- **管理者が外せる**：自動判定を通った手紙も、管理画面で見て外せるようにする。

## 11. マップの位置の同期

位置そのものを送るのをやめ、「区間の式」と「時刻表」を送る。フロントとバックが同じ式を同じ時刻で計算すれば、定期的に合わせるのは時計のずれだけになる。

### 今ずれる原因

今のコードでは、原因は次の3つ。

- **速度一定で先読みしている**：フロントは「受け取った位置＋速度×経過時間」で進めている（useProbeMotion.ts）。バックは加速と減速をするので、速度が変わる区間ほどずれが積み上がる。
- **起点の時刻が違う**：受け取る位置は最後のtickの時点の物なのに、フロントは受け取った瞬間から進め始める。tickの間隔ぶん、いつも遅れて始まる。
- **ずれが大きいと飛ばす**：ずれが一定（snapDistance）を超えると、位置を一気に移す。これが「一気に移動」に見える原因。

### 新しい形

&#91;embedded content: 位置の同期 · バックが式と時刻表を送り、フロントが毎フレーム計算\]

- **送る物**：区間の式、時刻表、サーバーの現在時刻、太陽系の天体の軌道要素。取得するのは、区間が変わった時と、時計合わせのための数分ごとだけ。
- **区間の式**：始点と終点（物理座標、AU）、出発時刻、加速・巡航・減速の時間と速度。今の \_travel\_distance\_fraction と同じ形でよい。惑星へ向かう区間は、到着時刻の位置を終点にして出発時に固める。目標が動いても式は変わらない。
- **時刻表**：場面の時刻は区間の式から先に計算できるので、区間を決めた時点で作れる。
- **表示座標はフロントだけ**：物理座標から表示座標への変換は、フロントだけが持つ。バックは表示座標を計算も保存もしない。

### 時計の合わせ方

- 取得のたびに、サーバー時刻との差を測る。往復にかかった時間の半分を足して補正する。
- 差が変わっても一気に合わせず、数秒かけて少しずつ寄せる。
- 一時停止は、時刻表の中の「時間が進まない区間」として扱う。フロントに一時停止専用の処理は要らない。

### なめらかさを保つ決まり

- **時刻表のつなぎ目**：対応点を直線でつなぐと、つなぎ目で見かけの速さが急に変わる。行き過ぎの起きない曲線（単調3次補間など）でつなぎ、速さの変化をなめらかにする。
- **区間の切り替え**：新しい区間は、前の区間の終点から始める。行き先を変えるのは到着した時だけにする。
- **それでもずれた時**：式の更新や時計の大きな補正で位置がずれたら、飛ばさずに1〜2秒かけて寄せる。ずれの大きさは記録し、大きなずれを不具合として見つけられるようにする。

### 2つの言語で同じ式を持つ

- PythonとTypeScriptで同じ式を書く。Python側で「時刻 → 位置」の答えをJSONに書き出し、TypeScriptのテストで同じ答えになるかを確かめる。
- 式が複雑になったら、バックが区間を細かい点（時刻、位置、速度）に分けて送り、フロントはなめらかな曲線でつなぐだけにする方法に切り替えられる。

## 12. デバッグ

本番は現実の1日に1本だが、デバッグでは待たずに場面を進め、同じ場面を何度でも書き直せるようにする。

### 時計の切り替え

- 公開の間隔を設定で変える。本番は24時間、デバッグは数秒〜数分、または手動。
- 手動のときは「次の場面へ進める」操作（管理画面のボタンとコマンド）で、1場面ずつ進める。
- デバッグ用のDBは本番と分ける。本番の世界や手紙に触れずに試せる。

### LLMを使わずに確かめる

- 今の mock.py を残し、LLMをモックに切り替えられるようにする。航路と時計の確認が、速く、費用もかからずにできる。
- LLMなしで100場面分の航路と時刻表を一気に出し、表で確かめる（13章の段階3）。

### 同じ場面を書き直す

- ログごとに、LLMに渡した入力（場面、見え方、手紙など）を保存する。
- プロンプトを変えて、同じ入力からログだけを書き直せるようにする。世界を進めずにプロンプトを調整できる。
- 世界はシードで固定し、いつでも同じ状態から始め直せるようにする。

### 位置のずれを見る

- 時刻を指定すると、バックが計算した位置を返すAPIを用意する。
- マップにデバッグ表示を付け、フロントとバックの位置の差を数字で出す。

### 手紙を確かめる

- テスト用の手紙をまとめて入れる操作を用意し、選ばれ方と、不適切な手紙が止まるかを確かめる。

## 13. 実装の進め方

今のコードの上に足さず、航路と見え方とログ生成の部分を作り直す。画面（Nuxt、Three.js）、時計、管理者機能はそのまま使う。

### 残す物と作り直す物

- **残す**：Nuxt の画面、Three.js のマップ（表示座標の計算だけ差し替える）、シミュレーション時計、管理者のログインと操作、JPL Horizons と NASA Exoplanet Archive の取り込み、LLMの接続部（openai\_compatible.py、factory.py）
- **作り直す**：simulation.py の行き先決定（navigation\_director、avoid\_stagnation、recovery\_action まわり）、固定の目印（外縁航路標など）、frontier ring の生成、観測事実の文字列づくり、フロントの位置の先読み（useProbeMotion.ts）
- **消す**：同名で重複している関数

### 段階

1. **世界データ**：座標をAUに統一し、行き先の共通の型を作る。太陽系の主な天体に見た目のデータを手で入れる。
2. **見え方の計算**：入出力だけの関数として作り、既知の値と照らし合わせるテストを書く（土星を200万kmから見ると満月の約6倍、など）。
3. **航路計画**：規則を1つの関数にまとめる。シードを固定して100区間分の航路を表に出し、距離の伸び方と寄り道の回数を目で確かめる。
4. **ログ生成**：新しいプロンプトで、太陽系の中の数場面を実際のLLMで試し書きする。
5. **謎**：1件だけ入れて、兆候から余韻まで通す。
6. **恒星間**：恒星カタログ、空白を埋める生成、休眠と目覚めを入れる。

1〜4が終われば、太陽系の旅としては成り立つ。
